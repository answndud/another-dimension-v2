# ADR 0004: 백업 형식 버전 정책과 구형 형식

- 상태: 채택
- 관련: [README](../../README.md)의 백업 형식 표

## 맥락

백업은 사용자가 파일로 직접 옮기므로 오래된 파일이 계속 들어옵니다. 형식이 개선될 때마다 이전 형식을 읽을 수 있게 두면 보호가 약한 형식이 공격 표면으로 남습니다.

## 결정

1. 새로 만드는 백업은 항상 최신 형식입니다. 단일 대화는 ADBACK7, 묶음은 ADPACK3입니다.
2. 최신 형식은 파일마다 무작위 ID, 프레임 인덱스, 종료 프레임을 인증 데이터에 결속하고, 묶음은 대화 수·순서·자식 바이트를 HMAC으로 인증합니다. 선택적 비밀번호는 Argon2id로 유도하고 신원 키와 HKDF로 결합합니다.
3. 형식을 바꿀 때는 새 매직 문자열을 추가하고 이전 형식 읽기는 유지합니다. 기존 데이터를 열지 못하게 하는 변경은 하지 않습니다.
4. 보호가 약한 구형 형식(ADBACK2, ADBACK6, ADPACK1, ADPACK2)은 서버가 기본적으로 거부합니다. 사용자가 형식별 위험을 확인했을 때만(`allowLegacy: true`) 가져오거나 재보호합니다. 재보호도 같은 확인을 거치는 이유는, 구형 파일을 신원 키로 인증된 새 컨테이너에 담으면 이후 가져오기에서 경고가 사라지는 우회 경로가 되기 때문입니다.
5. 서명이 없는 메시지는 기록 화면에서 "서명 없음 · 미검증"으로 표시합니다. 구형 형식으로 가져온 위조 가능성이 있는 메시지를 사용자가 구분할 수 있게 하기 위해서입니다.
6. 다음 형식은 차단하지 않습니다: ADBACK1, ADBACK3–5(파일 전체가 신원 키로 인증되어 키 없이는 만들 수 없음), ADBACK7, ADPACK3. 처음 계획은 ADBACK1·ADBACK3도 포함했지만, 이 형식들은 위조 경로가 없어서 막으면 정당한 오래된 백업을 쓰는 사용자에게 불필요한 확인만 늘립니다.

## 근거

ADBACK2는 키가 비밀번호에서만 유도되고 메시지에 서명이 없습니다. 비밀번호를 아는 사람은 상대가 보낸 것처럼 보이는 기록을 만들어 병합시킬 수 있습니다. 이 문제는 [SF-002](../security-fixes.md)에서 고쳤고, 남은 한계는 [SECURITY.md](../../SECURITY.md#known-weaknesses)에 적었습니다.

## 대안

- 구형 형식을 영구히 지원: 위조 경로가 남습니다.
- 구형 형식 즉시 삭제: 사용자가 가진 오래된 백업을 열 수 없게 됩니다.
- 한 번 변환하는 도구 제공: 장기적으로 유력하지만 범위가 큽니다.
